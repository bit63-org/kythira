# Requirements Document

## Introduction

This spec gives the virtual HSM (`.kiro/specs/virtual-hsm/`) the layering
rules `.kiro/specs/kinesis-independent-layers/` sets for Kinesis: each
layer can run as its own process or cluster, co-located operation stays
the default and is never required to change, and a running deployment can
move from co-located to independent operation and back. It follows Clark's
request of 2026-11-17 ("Do the same for DDB, KMS, and HSM") and his rules
that every spec tests its migration paths and, as far as possible,
interoperability with the real AWS counterpart (CloudHSM).

The HSM is different from the data services in one way that drives the
whole design: **the master key (MK) is the boundary**. Splitting layers is
worth doing here mostly because it lets the nodes that hold the replicated
key store never be unsealed and never hold a share, and the nodes that are
unsealed hold no durable key store. Every requirement below keeps the
virtual HSM's guarantees (Raft log and snapshots hold only ciphertext;
keys are generated by an unsealed node and only wrapped bytes are
proposed; existence and attribute checks before every use; Shamir over the
MK only).

### The HSM's layers

Read from the design and from `services/hsm/` on main:

1. **Endpoint**: where PKCS#11 clients connect (`wire_server.hpp`: framed
   requests over TLS 1.3 with client certificates, or a Unix socket).
2. **Crypto**: the session layer (`session_layer.hpp`: logins, sessions,
   multi-part operation state), the key vault (`key_vault.hpp`: the MK and
   unwrapped token keys in the secure arena), the key cache, the
   mechanisms, key generation and wrapping, unseal and node unseal
   (`unseal.hpp`, `node_unseal.hpp`).
3. **Store**: the catalog group and one group per token on the multi-raft
   host (`hsm_host.hpp`, `catalog_state_machine.hpp`,
   `token_state_machine.hpp`): tokens, bindings, wrapped token keys, the MK
   check value, objects, attributes, wrapped material, PIN verifiers and
   login counters. The state machines never use the vault (checked on
   main), so the store already needs no MK.

The session layer reaches the store only through `hsm_store`
(`hsm_store.hpp`), a virtual interface of reads, proposals and
`read_barrier`. That is the seam between crypto and store, and it exists
today.

Sessions are bound to the client's connection (virtual HSM design,
"Sessions are node-local"), so the endpoint cannot be separated from the
crypto layer without either relaying connections whole or replicating
sessions. This spec takes the first: an endpoint node is a layer-4 relay
that pins each connection to one crypto node and never terminates the
client's TLS, so it never sees a PIN or a key.

The shared core pieces come from the Kinesis spec: per-node roles, layer
identities, the route cache and the layer membership group (for endpoint
discovery only; crypto membership is security-critical and lives in the
HSM catalog, Requirement 5).

**Scope**: roles; a remote `hsm_store`; remote read barriers that also
carry the seal state; crypto membership and share distribution in a split
layout; the endpoint relay; migration both ways; tests including CloudHSM
interoperability.

**Out of scope**: replicating PKCS#11 sessions; threshold cryptography;
changing which PKCS#11 functions and mechanisms are offered.

## Glossary

The Kinesis spec's glossary applies. In addition:

- **Crypto node**: a node with the `crypto` role. It can be unsealed.
- **Store node**: a node with the `store` role: a member of the catalog
  and token groups. It is never unsealed.
- **Crypto member list**: the catalog's list of identities allowed to be
  crypto nodes, to receive MK shares and to ask for them.
- **Seal state**: the catalog's seal epoch and MK generation, which every
  crypto node must follow (virtual HSM requirement 4.7).

## Requirements

### Requirement 1: Co-located operation stays the default

**User Story:** As an operator, I want the virtual HSM to run as it does
today unless I ask for independent layers.

#### Acceptance Criteria

1. With no new setting a node SHALL run all three roles, and `hsm_node`,
   `hsm_ctl`, `libkythira_pkcs11` and `kythira_node` SHALL behave as today.
2. In a co-located cluster the crypto member list SHALL be the store
   members, so node unseal, init and rekey behave as today.
3. Every existing HSM test, `pkcs11test` run and docker-chaos scenario
   SHALL pass unchanged.

### Requirement 2: Roles

**User Story:** As an operator, I want the replicated key store on nodes
that can never be unsealed.

#### Acceptance Criteria

1. A node SHALL take its role set from `KYTHIRA_HSM_ROLES`, a subset of
   `endpoint`, `crypto`, `store`; default all three.
2. A node without `crypto` SHALL NOT accept an unseal (operator or node),
   SHALL NOT hold or receive a share, SHALL NOT create a key vault, and
   SHALL refuse every PKCS#11 call it would have to answer itself.
3. A node without `store` SHALL NOT be a member of the HSM's groups and
   SHALL NOT open the engine or a Raft log.
4. A node with `endpoint` but not `crypto` SHALL relay connections
   (Requirement 6) and answer nothing itself.
5. A role set the node cannot serve SHALL stop it at start with the reason.

### Requirement 3: Remote store

**User Story:** As a crypto node that is not a store member, I want the
same `hsm_store` with the same guarantees.

#### Acceptance Criteria

1. A `remote_hsm_store` SHALL implement `hsm_store` over a store API on
   store nodes: catalog and token reads, `propose_catalog`,
   `propose_token`, and `read_barrier`.
2. Proposals SHALL go to the group's leader; a non-leader SHALL answer
   not-leader with a hint and never forward further. An ambiguous failure
   SHALL answer `CKR_DEVICE_ERROR`, as today, so a login failure is never
   counted twice.
3. Reads SHALL return wrapped material only. The store API SHALL have no
   call that returns or accepts an unwrapped key.
4. The crypto node SHALL cache wrapped objects by `(handle, version)` and
   unwrapped keys in the secure arena as today.

### Requirement 4: Read barriers and seal state

**User Story:** As a security reviewer, I want a destroyed or narrowed key,
a seal or a rekey to take effect on remote crypto nodes exactly as on
co-located ones.

#### Acceptance Criteria

1. `read_barrier(token)` on a remote crypto node SHALL ask the token
   group's leader for a read-index round and return only after the answer
   names an applied index at or past it, with the object versions the
   caller asked about.
2. Every barrier answer SHALL carry the catalog's seal state. A crypto node
   that sees a newer seal epoch or MK generation than its vault SHALL seal
   itself before answering the call (virtual HSM requirement 4.7).
3. A barrier that cannot be had SHALL answer `CKR_DEVICE_ERROR`, never a
   stale result.
4. A crypto node SHALL also follow the seal state between calls (a watch or
   a poll bounded by the maintenance interval), so an idle crypto node
   drops its keys after a `seal` command without waiting for a call.

### Requirement 5: Crypto membership and shares

**User Story:** As a security officer, I want only nodes I admitted to be
able to hold or ask for MK shares.

#### Acceptance Criteria

1. The catalog SHALL hold the crypto member list: identities, admitted
   and removed by an admin command with the same authorization as today's
   membership changes. It SHALL NOT be filled from the layer membership
   group or from self-announcement.
2. Node unseal SHALL release a share only to a caller whose layer identity
   has the `crypto` role and is on the crypto member list (today: a
   current member of the HSM groups).
3. Init and rekey in node mode SHALL hand share i to the i-th crypto
   member, with `n` the crypto member count. Store-only nodes SHALL get no
   share and SHALL NOT count toward `k` or `n`.
4. Removing a crypto member SHALL require a rekey before the removal is
   reported complete, because the removed node keeps its old share; the
   admin API and `hsm_ctl` SHALL say so and offer the rekey in the same
   step.
5. Adding a crypto member SHALL give it a share only through a rekey (node
   mode) or leave it to operator unseal (operator mode).

### Requirement 6: Endpoint relay

**User Story:** As an operator, I want to expose the HSM to clients
without putting the MK on the host they connect to.

#### Acceptance Criteria

1. An endpoint node SHALL relay each client TCP connection whole to one
   crypto node and SHALL NOT terminate the client's TLS, so client
   certificates, PINs and key bytes are never visible to it.
2. It SHALL choose a crypto node that is unsealed and healthy, preferring
   the least connections, and keep the connection pinned for its life.
3. When the crypto node fails, the endpoint SHALL close the client
   connection; `libkythira_pkcs11` reconnects and re-logs-in sessions as
   it does after a failover today.
4. Unix-socket clients SHALL always use a crypto role in their own node.
5. An operator MAY use any layer-4 load balancer instead of an endpoint
   node; the endpoint role exists for health-aware pinning and drain.

### Requirement 7: Authentication between layers

**User Story:** As a security reviewer, I want every internal HSM call
authenticated and limited by role.

#### Acceptance Criteria

1. Internal calls SHALL use layer identities with `hsm` as the service,
   as Kinesis Requirement 7 defines them, and SHALL refuse plaintext with
   no opt-out other than loopback tests.
2. The store API SHALL accept only `crypto` and `store` callers; share
   requests only `crypto` callers on the crypto member list.

### Requirement 8: Co-located consumers

**User Story:** As the KMS, the CA, Kinesis or IAM, I want PKCS#11 to work
whichever HSM layers sit beside me.

#### Acceptance Criteria

1. `hsm.client` (the native client) SHALL be published in-process only by
   a node with the `crypto` role; elsewhere consumers SHALL use
   `libkythira_pkcs11` or the wrapper's network backend.
2. Consumers SHALL be tested against a co-located and a remote crypto
   node.

### Requirement 9: Live migration

**User Story:** As an operator, I want to move a running HSM between
layouts in both directions.

#### Acceptance Criteria

1. Splitting the store off: store-only nodes SHALL join the catalog and
   token groups as learners, catch up through the ordinary snapshot path
   (ciphertext only), be promoted, and take over as the co-located nodes
   leave the groups through leadership transfer and removal. The crypto
   member list SHALL be set from the co-located members before the first
   store-only node joins.
2. Splitting crypto off: crypto-only nodes SHALL be admitted to the
   crypto member list and given shares by a rekey (node mode) or unsealed
   by operators; the old crypto members SHALL be removed with the rekey of
   Requirement 5.4.
3. Folding back SHALL use the same operations in the other order.
4. During a migration no object SHALL be lost; every key SHALL keep its
   handle, attributes and material; a destroyed key SHALL never be used
   after its destroy committed; and at no step SHALL a share or the MK
   reach a node without the `crypto` role.

### Requirement 10: Testing

**User Story:** As a maintainer, I want every layout, every migration path
and CloudHSM interoperability tested.

#### Acceptance Criteria

1. `pkcs11test`, the `pkcs11-tool` and `pkcs11-provider` scripts and the
   consumer tests SHALL run against a split layout (endpoint, crypto and
   store apart).
2. Every migration path SHALL have its own test in both directions:
   store split off and folded back, crypto split off and folded back
   (with rekey), endpoint added and removed, and the whole path both ways
   with a stop and reversal midway, under a sign/decrypt and
   key-administration workload, checking Requirement 9.4.
3. A docker-chaos scenario SHALL run the full path both ways with kills of
   each layer and a seal mid-path, on Docker and rootless Podman.
4. The plaintext scan SHALL run over every store node's data directory,
   Raft log and snapshots and find no key material, no share and no MK;
   and over every endpoint node and find nothing.
5. Interoperability with real AWS SHALL be tested as far as AWS allows:
   the consumer suite (CA, Kinesis, IAM through `kythira::pkcs11::module`)
   run once against the split virtual HSM and once against AWS CloudHSM's
   PKCS#11 library with the same configuration change only; and a public
   key generated on either side verifying signatures made on the other.
   CloudHSM runs bill per HSM-hour, are dispatch-only, need Clark's go in
   his own words each time, and delete the cluster when done.

### Requirement 11: Documentation

**User Story:** As a security officer, I want to know what each layer can
reveal if compromised.

#### Acceptance Criteria

1. `services/hsm/README.md` SHALL describe the layers, a table of what a
   compromised node of each role exposes (store: ciphertext only;
   endpoint: nothing but traffic metadata; crypto: the MK while unsealed),
   the crypto member list, the rekey rule for removals, and the migration
   runbook.
