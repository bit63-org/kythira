# KMS module

A KMS-compatible key management service for Kythira: AWS KMS's JSON 1.1 API
(`TrentService`), so the AWS CLI, the SDKs and the AWS Encryption SDK work
against it unchanged. It holds no key material itself: every key's material
is a non-extractable object on the virtual HSM's `kms` token
(`services/hsm/`), and every request is authorized by IAM with the key's
policy (`services/iam/`). Like the HSM it is software, so key material is in
host memory while in use (`doc/hsm.md`). The spec is
`.kiro/specs/kms-compatible-api/`; this directory follows
`services/README.md`.

Built when `CONFIG_KMS=y` (`services/kms/Kconfig`, off by default, needs
`CONFIG_HSM` and `CONFIG_IAM`). `configs/ci_full_defconfig` turns it on, so
ci.yml builds and tests it; `configs/ci_no_kms_defconfig` is the module-off
configuration `.github/workflows/kms-module.yml` checks.

The KMS cases of IAM's policy corpus (key policies, delegation,
cross-account use, `kms:ViaService`, encryption context conditions) are in
`services/iam/tests/corpus/evaluate/kms_key_policies.json`, where IAM's
evaluator runs them.

With IAM off the KMS runs on static keys, and the static roles decide
alone: read-only may describe and list (including `GetKeyPolicy` and
`ListKeyPolicies`), read-write adds the cryptographic operations, and
admin may do everything. Key policies are still stored, returned and
checked for size and JSON form, but they are not evaluated, and a policy
that would deny the admin does not. Grants are stored and listed but
allow nothing (`front_end_config::evaluate_grants` is off on static
keys).
Turn IAM on before relying on a key policy.

The published client (`kms.client`, in process and over HTTPS) and the
Kinesis and DynamoDB integrations follow in tasks 12 to 20 (`.kiro/specs/kms-compatible-api/tasks.md`).
